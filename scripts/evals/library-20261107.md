## PDF 预处理模块

- 资料库中 20 个 PDF 网址：18 份取得正文，2 份因 polimi.it 服务器中断 SSL 连接记为 `network_error`。
- 首版使用 pymupdf4llm 默认的版面模型，单项最长 314 秒、整批 310 秒以上；改为文字层转换后整批 37 秒，同一份 5 页 PDF 由 2.9 秒降到 0.5 秒。
- 提取引擎变化后不再发条件请求：此前因 304 保留旧提取结果的 10 份重新转换为 `changed`，内容相同的记为 `unchanged`。
- scupgkg.cn 以 HTTP 200 返回“安全验证”HTML 页面。加入 `%PDF-` 文件签名检查后记为 `restricted`（`captcha`，疑似），没有覆盖正文；加入检查前被误收的 1 份正文已清除。

## 迟到结果（`stale`）

`scripts/tests/test_library_stale.py` 在恢复演练资料库上运行，3 项通过：

- 维基百科随机条目两次真实抓取得到不同正文，先开始的尝试后完成时记为 `stale`，资料保留后开始尝试的正文，迟到结果写出的文件被删除。
- example.com 两次抓取正文相同时同样记为 `stale`，不写新文件。
- 另一连接持有备份锁时，旧正文删除返回 `deferred` 且文件保留；锁释放后删除成功。

首篇正文早于搜索返回：每个渠道返回后立即开始抓取它的结果，搜索返回时付费 API 与全部渠道两组已有 94 至 158 项完成。搜索返回时间由最慢渠道决定，CLI 自身的启动、归档与索引共约 1.5 至 4 秒。

固定任务回放（253 项，`.work/library-dev/fetch_bench.py`）：改造前并发 16 整批 102.3 秒；常驻提取进程后 50 秒；最终配置（并发 32、连接池、jsdom 迭代修正、PDF 独立进程）23.9 秒，50% 项 12.3 秒，95% 项 19.7 秒。

各项改动的实测依据：

- CLI 导入 `elasticsearch` 稳定耗时 1.3 至 1.4 秒，原先发生在搜索开始前；改为搜索期间后台导入后，单渠道搜索中 CLI 自身开销由约 2.8 秒降到 0.57 秒。
- 每项各自写索引时，首批任务项要等待执行器导入 `elasticsearch`（实测单项最长 7.5 秒），且等待期间占用数据库连接，使其他项 `wait_db` 达到 6 秒；改为单个索引线程批量写入后各项 `wait_db` 为 0。
- 一份 25 MB、197 页的 PDF 下载 31.3 秒、转换 29.2 秒，并发运行时单项达 189 秒；流式下载与转换原先都没有总时限。现在两者分别受单项时限限制，超时转换的进程被终止并在下次按需重启（时限 3 秒时 3.1 秒返回，随后的转换在新进程中完成）。
- 执行器以低于正常的优先级运行时，CLI 归档后返回快约 1 秒，但 Microsoft Defender 等常驻程序占用约 1.5 个核时提取明显变慢（中位 797 毫秒，最长 15.5 秒），因此执行器保持正常优先级。

渠道进程启动开销：每个渠道是一个独立 Python 进程，单独启动并导入 `curl_cffi`、`lxml` 约 0.57 秒；23 个同时启动时每个需 1.6 至 2.4 秒，46 个同时启动时 2.1 至 4.1 秒（`.work/library-dev/spawn_burst.py`）。baidu_direct 单独运行 1.48 秒，在 23 个渠道中运行 3.4 至 4.0 秒。
